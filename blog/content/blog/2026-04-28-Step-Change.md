# Step Change

*April 27, 2026*

Software development is changing. But not that much.

That's my theory. I don't think code is obsolete, or that you don't need engineers to get the job done and own the work. For the foreseeable future, we'll still need technically skilled people designing database schemas, setting up integrations, assessing security measures, prioritizing work, designing architecture, investigating incidents, and yes even reading, writing, and understanding code line-by-line. There's still enough work for a person here that most of the time, an engineer runs one or zero agents at a time. Maybe one in the background, one in the foreground.

All that being said, I do think we're getting to a place where most code is generated, and codebases look rather different than before. Mainly, I expect they'll end up being more consistent, and more comprehensive. More tested, more mocked, more specified, and just more of it. Healthy, transparent and organized. This is because LLMs provide both the means, and the necessity, to make codebases consistent, accessible, and well tended.

I could be wrong, but it's still fun and useful to think about where we're headed and make a prediction. I expect things will turn out different than my expectation, but it's still important to have a vision of where you're headed while you're getting where you're actually going. It's a journey with twists and turns.

# Agentic Stacks

Vibe coding, as an approach to software development, is fundamentally limited. When you rely entirely on an LLM to structure and build out a piece of software, it will make decisions somewhat randomly, including whether to include you in decision-making. That randomness leads to inconsistencies across the codebase, and is heinously inefficient. If the agent has to decide each time how to structure, test, and validate what is built for every layer of a codebase, it's basically yak-shaving over and over again, and it will tend towards applying band-aids than coming up with durable solutions in order to scope the time and tokens spent. And any durable solutions that it *does* generate will be inconsistently applied. Vibe-coding often turns cancerous, which can be fatal to a non-trivial project, as the inconsistencies, shortcuts, and available solutions compound and multiply. It's risky and it's costly, and just throwing more agents at the problem mitigates some of the risk while exploding the cost.

The solution to this problem is highly-opinionated stacks where most logic is generated by agents with heavy guidance and validation. An agentic stack delivers this guidance by providing some tool for doing rote, common work like adding a new API endpoint or mobile view. This tool isn't just another coding agent powered by the most advanced model and handed a markdown file. The tool is a collection of workflow scripts which generate boilerplate, feed prompts to agents, and run validation checks. This gives agents a good, consistent starting place, and adds some much-needed enforcement and automated feedback telling agents to fix the tests or the types or what have you.

Besides including a workflow tool, an agentic stack also needs to come fully-loaded with proscribed solutions, libraries, and services. For example an agentic web stack would include decisions on, solutions for, and glue between:

- CI/CD
- Hosting
- Blob storage
- Secret storage
- Logging
- Analytics
- Background processing
- Identity and auth
- Database
- Caching
- Internationalization
- HTTP Server
- Third-party integrations
- Static pages
- Dynamic pages
- Design system
- CRM
- Offline mode
- Streaming
- API specification and design
- Shared data schemas and types
- Containerization and orchestration
- Local development
- Unit, integration, and E2E testing

And more! Basically these stacks need to come with all the *stuff* which is used in most if not all non-trivial web applications. The workflows that the stack provides helps build out components which leverage all these chosen dependencies.

When you build most things, and especially new things, with those scripts, what you end up with is a codebase which is much more consistent and useful, built much more quickly and cost-effectively than having one designed ad-hoc by agent committee.

- When the product does not work as expected, it's much cheaper and faster (for either agent or human) to know where to look and to fix the problem, and how to fix it.
- If you need to make sure your application is secure, it's much easier to audit for missing access controls.
- When making changes or small additions, the codebase is full of consistent examples so that, even if you don't use a script to manage the work, the agent is much more likely to find and apply the correct patterns to follow, rather than making its own way. The path of least resistance is the correct one.
- Major migrations are also much cheaper because things are already in a consistent place, which makes it simpler to design a repeated process (or for a freeform agent to get into a nice groove) to move everything over.

A stack that proscribes that many solutions needs to be fully owned by the individual or organization that owns the product. An open-source web stack that includes all the features above will still probably not include every platform feature a given product needs, nor will it have the best solutions for a given product. While most businesses depend on other organizations to provide coding languages, server software, and hosting services that power the company's product, the company itself still owns the combination of those things, and I expect that to continue to be the case.

## Why so certain?

I am confident systems will move in this direction because I've been experimenting with and experiencing this approach more and more over the last year and been very happy with the results. I've built four products with successive iterations of my own web stack and workflow tool, getting better results the more I invest. At this point, I can dependably generate high-quality, fully featured, and well structured codebases, without investing in a premium plan or managing a fleet of agents.

By using these workflows, I get to be confident in the following (and more):

- Database queries and HTTP endpoints are completely separate.
- All database queries return errors instead of throwing them so the errors are typed.
- Third party integrations all have mock implementations.
- My product's own APIs all have mock implementations.
- Tanstack query caching is tested.
- Vue components have composables and Vue-independent logic each refactored out and tested separately.
- Vue components are decomposed with minimal props, opting to interface directly with Tanstack Query instead of prop drilling.
- Vuetify is leveraged heavily over custom CSS.
- SPA code and data are loaded in parallel.
- User-facing strings are ready for internationalization.
- Database, server, API spec, Tanstack queries, and SPAs all have their own npm packages.
- All these packages are structured consistently and are appropriately unit and integration tested.
- If I prompt an agent to extend or add a small piece to an existing product, the new code will tend to have these qualities as well.

Part of product development has been iterating on these templates and workflows when I notice agents building things that cause product, security, and maintainability problems. It's been gratifying to implement solutions and know that that they will be enacted consistently going forward.

Agents are good at some things but they are not reliable or consistent. You can't depend on them to find the right instructions at the right time and follow them consistently and through to the end; this is not because they're flawed, it's because it takes time and effort to get a complete picture and determine an answer that may or may not exist. However, when they are given just the information they need and not expected to police themselves at the same time and make the perfect call, they produce better results cheaper, faster, and much more consistently. Being provided a starting point, specific guidance right when it's needed, and checks to ensure directions were followed, set them up for success and leave them to do what they're useful for. And in the years they've been on the market, that fundamental quality has not changed. And with prices rising and the honeymoon phase ending, I think it's time to start really figuring out how to harness them better so they can more consistently and effectively boost productivity without breaking the bank or the environment.

## What does coding in agentic stacks look like?

1. **New features and products are generated with the highly structured, heavily guided workflows.** This sets the standard for that area of the codebase, getting everything set up on the right foot. This looks like how a lot of agentic works already looks: you write out a plan and you have the agent follow that plan. What is different from other agentic workflows is that the plan is a script, written in code, not just a markdown document.
2. **Smaller features and changes may use a freeform agent**, because the codebase is in a good place and the agent is not likely to diverge from the patterns and best practices that already exist.
3. **Reviews focus on the constraints and expectations more than implementation**. It's more important to make sure the database model, API specification, integration scope, and product experience fit the needs of the person or business. The generated implementation will largely be fine, and issues can be identified and addressed reactively with well instrumented and organized code. The writing and review of the details of the implementation is where you save time as a software engineer, and building within an agentic stack delivers consistent enough results that you *can* spend your attention elsewhere.
4. **More time is spent investing in the platform and best practices as a whole**. When there *are* issues that come up, and it's an issue that is likely to recur or is already recurring, it's best to improve the framework and the workflows to reduce their occurence systemically. If competing standards are cropping up, one should be chosen and everything else migrated over. Coding becomes more like gardening where you're continuously pulling weeds and pruning wayward branches.

## How does the code written in an agentic stack look different?

1. **More comprehensive**. Because generating pieces as part of a workflow is so reliable, I include more for each *thing* than I used to. For example, I don't only have Tanstack Queries generated. I also have the agent create a mock implementation for the API request the query wraps around, and a test that uses both. This way I can have the agent test the caching behavior, and the mock API implementation can be reused reliably in other Vue component or composable tests. In a non-agentic stack it's sorely tempting to skip some of those steps for the short-term gains, but since it comes "for free" with everything that's built, I know these steps are never getting skipped.
2. **Easier to debug**. Once you've figured out how a codebase is structured, you can be confident that the layering and separation of concerns are adhered to, and you don't need to "learn the local language" when jumping from one part of the codebase to another; you know where to look for what you're looking for. You know what tools you have and what's measured and tracked and how to access it. This is actually important because, since you're spending less time working on the codebase directly, it's the much easier to forget about how it was set up before.

## What are the new bottlenecks?

So an agentic stack saves a bunch of time in building and maintaining code compared to what come before it. With that much time saved, where is time being spent instead?

1. **Stack management.** Let's say you have the ideal stack. Well, someone's ideal stack. You'll still probably need to evolve it for your use case. There's no one-size-fits-all stack out there, and different parts of the stack need different levels of investment and feature-richness depending on the use case. If you already have a stack, then little has changed. If you're starting fresh in this world of agentic stacks you would hopefully find a stack with a set of services which covers most of your needs, then you fork it and spend some time reworking the stack to suit your business.
2. **Product constraints**. These are the areas that still need decisions made and well thought out. The constraints are things like your database model, your API, your interface, and your integrations. What can the user do? What can the server do? What can the database do? What can be done using 3rd party services? What should they not be able to do, what are the invariants? These are critical enough decisions in designing a product that these still require a technically minded person to own and make sure are correct for what the business needs.
3. **Product iteration**. Let's say you want your own recipe app. You could tell an agent "I want a recipe app, and use this agentic stack to do it", it'll probably be a fine and well structured, maintainable recipe app. But it still won't be yours. To make something yours, you need to spend time deciding what is important to you, how you want it to work, how it should be structured. And part of figuring that out is discovery.

I think there's a question what kinds of products we'll have that are enabled by LLMs, and one possibility is an explosion of custom-built products. These could be products individuals use to automate their day, or products companies build to ween themselves off Salesforce.

I think there'll be (and there is) some of that for sure, but the bottlenecks above are still going to keep custom solutions from truly attaining significant adoption.

It's sort of like my desk, which I built out of wood. It took seventeen full days of my time to design, construct, and finish it, and it's extremely tailored to my situation and desires. I had a bunch of tools to expedite the process, but it still took more time (and probably more money) to attain this custom desk, and the drawers and finish are still not as smooth and consistent as a purchased desk. I also spent years experimenting with different layouts before deciding I knew what I wanted. It was quite fulfilling and totally worth it to me that I have my own custom desk, but that's not appropriate for most people, and in a similar way the cost of figuring out what you want and iterating your way to find that is not worth it to most people and organizations. Off-the-shelf products still work fine for most situations, and the cost of crafting a custom solution is still a barrier to an explosion of fully-custom-tailored solutions for home and business.

## What comes next?

I think it'll take many years for the industry to move in this direction, if I'm correct. Assuming we get to the point where there's a healthy ecosystem of stacks with generative tools baked in... Then I think overall software will be more dependable.

Though it will continue to be prohibitively expensive for people to build their own custom solutions end-to-end, I do think there's an opportunity to enable people to customize their own experience on top of existing products. Think bookmarklets but more deliberately supported by products themselves.

For example, a website could provide a specification for the product's API to an agent, and a hook for inserting buttons or links or new pages. An agent could then write code according to the user's instructions, custom to the user's needs, leveraging that API and those hooks. This way users can create durable, useful extensions without having to go through a marketplace, or creating the extension by hand. If the user wants to integrate two or more products together, as long as all products support user extensions, then the user can set up the integration the way they want. This would still be a barrier to entry, but a much lower one than having to build your own custom product from scratch.

It's also interesting to think about how much further the software creation process can be automated, in particular those bottlenecks above. I can imagine an automated process where agents identify ways to improve the stack based on usage, and they prove themselves dependable enough to make good product constraint and iteration decisions. But I think these will have diminishing returns, because there is an irreducable level of decisionmaking someone needs to make, and to make good decisions you need to understand the tradeoffs, and understanding the tradeoffs requires some level of skill and experience.

At some point you have to decide what do you want to spend your time and attention on, and you get what you pay for.

## What can a company do now?

1. Recognize the limitations of generative AI as it is structured (or unstructured) right now. Avoid using it for adding to debt-ridden codebases, instead use it and other tools to reduce the debt and build a better environment before using agents to add on top. Identify bad patterns that chatbots profligate and dedicate effort to remove those bad patterns or gaps in best practices.
2. If you're starting from scratch, make sure to set aside time to deliberately provide a good foundation to build on. I've seen codebases initially built without AI and with AI, and ironically, the codebases initially set up without AI are better for AI to work in, because of how opinionated and consistent they are. Start from a good place.
3. Experiment with scripts for generating new code in a consistent and heavily guided, templated manner. You may already have scripts or CLI tools for generating boilerplate, incorporate chatbots into those scripts to make building new code happen automatically and quickly and dependably. This will help you get to, or start from, a good place for agents to do great work.
